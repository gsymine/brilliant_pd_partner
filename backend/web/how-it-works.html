2 · Agent flow

What happens behind the click

Three agents with one job each, handing work to each other through the backend. One Communication Agent session per vendor runs in parallel; extraction starts only once every vendor conversation is closed.

  1. You click Start sourcing.
  2. The orchestrator creates the run and opens one ZooWork session per vendor.
  3. Each Communication Agent session emails its vendor and keeps the conversation going.
  4. Every fact is saved to Vendor Memory with its source quote; follow-ups ask only for gaps.
  5. The gate opens when every conversation is complete, declined or stalled (or you stop waiting).
  6. The Extraction Agent turns all threads into one structured offer per product.
  7. The Analysis Agent gets all numbers from the costing tool and writes the recommendation.
  8. You review the ranked products, with photos, and decide.
3 · Solution design

Architecture

One backend serves the web app and drives the agents. Agents never touch email, the database or the math directly: they call tools, and the backend executes every tool call, scoped to one run and one vendor.

4 · Where ZooWork is used

ZooWork does the thinking. The backend does the doing.

Every judgement call runs on ZooWork Managed Agents. Everything that must be exact, safe or auditable stays in plain backend code.

ZooWork

Managed agents

4 hosted agents, created once and found again by labels. Each agent's skill.md is loaded as its instructions; a changed skill updates the agent on the next start.

ZooWork

Sessions as memory

One long-lived session per vendor conversation, days of back-and-forth in one context. Extraction and Analysis get one session per run.

ZooWork

Application-executed custom tools

Agents decide which tool to call and when. The run pauses, the backend executes the tool, and its result (or an error the agent can fix) goes back with resolve_custom_tool_call.

ZooWork

Event streaming

The backend streams each turn's events (stream_events), saves the cursor, and stops on run.finished. After a restart it resumes and finishes pending tool calls.

ZooWork

Idempotent operations

Agents, sessions and messages are created with idempotency keys, so a retry never creates a second agent or a duplicate turn.

ZooWork

Vendor role-play (demo)

A fourth agent writes vendor replies in "grounded" mode: it may only use what the vendor's original email says, and never invents a value.

ZooWork Communication Agent

  • send_email to this vendor only
  • read_thread full email history
  • save_vendor_facts fact + source quote
  • get_vendor_memory what is still missing

5 · Design principles

Why it is built this way

⚖️
Agents judge, code calculates

No number in a recommendation is computed by a language model.

🧵
One vendor, one session

Conversations never mix; each keeps its own memory.

🧠
Nothing is lost

Facts are versioned and keep the quote they came from.

🛡️
Vendor email is untrusted

Instructions hidden in a vendor's email are treated as data.

🙋
The human decides

Agents recommend; accepting products is always your call.
